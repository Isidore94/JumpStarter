# Playbook: review by reproduction

The reviewer's checklist. **Find what is wrong by running it, not by reading it.**

Reading a diff finds style problems and obvious logic errors. It does not find the
defects that matter, because those are the ones whose code reads correctly. Fully green
suites have shipped: a missing number read as a category literally named `"NAN"`; a link
tag that evicted the real tags it was meant to sit beside; a summary card printing 100%
where the truth was 30%. Every one of those was reviewable by reading and was not caught
until someone ran it.

You never modify the branch. Temporary edits for a reproduction are restored, and
`git status` is clean when you hand back.

---

## 1. Delivery, item by item

Read the packet and the full diff (`git diff <base>..<branch>`). For **every** numbered
item: delivered / partial / missing, with `file:line` on the branch.

An item silently dropped is a finding. So is an item delivered wider than specified — a
builder that widened the packet made a decision that was not theirs to make.

## 2. Run the tests

Run the branch's new and changed tests. Report counts. Then run the whole suite: a new
test that passes while it breaks four others is not a passing branch.

## 3. Fail-before-fix — prove it yourself

For each new test:

```
git checkout <base> -- <implementation file>
<run the new test>            # it must FAIL
git checkout <branch> -- <implementation file>
<run it again>                # it must PASS
```

**Name any test that passes on the un-fixed code.** A test that cannot fail proves
nothing, and it is worse than no test, because it will be cited as proof later.

The builder already did this. You do it again because the first proof was performed by
the party most motivated to see it succeed.

## 4. Reproduce claims against copies of real data

Every number in the handoff is a **claim** until you re-derive it. Copy the real file to
a temp path first — never write to a live store.

- Row counts, category names, distinct values: recount them.
- Rendered output: render it and read it.
- Timings: measure them on the same machine class.
- A claim about how many records are affected: run the query.

If the number differs from the handoff, that is a blocker, whichever direction it differs
in — a builder who was wrong about the count was wrong about something.

## 5. Invariant scan

- Any influence on a critical path (a decision, a score, a gate, an alert, a user-facing
  ranking) the packet did not authorise.
- Any expensive work on a latency-sensitive path: a file read, a full rebuild, a network
  call on a UI thread or in a hot loop.
- Any write to a store the packet did not name.
- Any statistic shown without its sample size, or shown as a verdict below its floor.
- Any behaviour change to something with consumers, without golden fixtures first.
- Uncertainty deleting: missing data treated as a negative rather than as unknown.

## 6. The eight traps

Check every one on every review. They are the specific ways a green suite lies.

1. **Old records have the key PRESENT and EMPTY, not absent.** A fixture that models an
   old record by omitting the field does not model the real file. Open the real file and
   look at an old row.
2. **A fixture generated by the code it is meant to pin is a self-portrait.** It will
   agree with any behaviour that code has, including the wrong one. Fixtures are pinned
   from the OLD code, and the commit is recorded.
3. **A test that asserts on source text proves nothing.** `assert "foo" in
   open("x.py").read()` passes for a commented-out `foo`. Assert on behaviour.
4. **`assert x or True` is a tautology.** So is any assertion whose failure branch cannot
   be reached — an `except: pass` around the assert, a loop over an empty list, a
   parametrisation that generates no cases. Running the test against the un-fixed code
   finds all of them.
5. **A positional lookup breaks when a field is prepended.** `row[3]`, `parts[0]`,
   unpacking a tuple by position, a CSV read by column index. Key by name.
6. **A window or threshold repeated as a literal is several different windows.** A
   "20-session window" that is `20` in two files and `21` in a third is a silent
   divergence. It must be read from one constant.
7. **A version, vocabulary or schema id asserted as a literal in a test** freezes the
   test to today's data and fails for the wrong reason tomorrow. Assert against the
   loaded definition.
8. **A derived value re-derived differently in two places will disagree.** One
   implementation, read by every surface. A headline number computed twice is a number
   that will eventually lie on one screen and not the other.

## 7. Ask-first

If the branch edits a file on the ask-first list, look for the record that the owner
answered — the decision quoted in the packet, or a dated record. **No record is a blocker
to NAME, not to decide.** You do not grant the permission; you report that it is missing.

## 8. Docs

- The "Active state at a glance" block is refreshed, with numbers measured on this
  branch.
- The packet's gate is a row in the gates table.
- The `CHANGELOG.md` inventory has an entry for what landed.
- `plan.md` is advanced or narrowed, and any gate still owed is retained.
- `docs/INTERNALS.md` has an entry for any new rule.
- `docs/README.md` is updated if a Markdown file was added or reclassified.
- `sha256(CLAUDE.md) == sha256(AGENTS.md)`.

## 9. Lint

Run it on the branch. A suppression added in this diff needs its reason beside it.

## The verdict

```
VERDICT: GO | NO-GO      BRANCH: <branch> @ <sha>
BLOCKERS (must change before merge; each with file:line and the reproduction that shows it):
 1. ...
ADVISORY (should change, not blocking):
 1. ...
DELIVERY: <item>: delivered | partial | missing - file:line
PROOF: tests run <files> <passed>/<failed>; fail-before-fix: <which failed on base>; lint <clean/N>
REAL-DATA CHECKS: <what you re-derived, with the numbers>
```

**A blocker** makes a number wrong, a gate unsatisfiable, a rule broken, or a
user-facing surface misleading. **Everything else is advisory.**

**Never pad.** A clean branch gets "BLOCKERS: none". A review that invents findings to
look thorough costs the next branch its trust, and the round after that its review.
